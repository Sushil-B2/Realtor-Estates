**Deployment today:** one Python process serving static assets + API + SSR pages.
**Deployment target (phase 2):** CDN/WAF → stateless API pods (containers) → Postgres 17 with RLS →
Redis (rate limits, sessions, queues) → object storage (documents, recordings) → worker pool →
vector index per tenant. The single-process build is a deliberate choice to keep the demo auditable
and dependency-free; the module boundaries already match the split (`app/api.py`, `app/agents.py`,
`app/store.py`, `app/security.py`).

### 1.1 Stack decisions (as built)

| Layer | Decision | Why | Rejected alternative |
|---|---|---|---|
| App tier | Python 3.13, **stdlib only** | Zero transitive CVEs, trivially auditable, runs anywhere | Node/Express (fine, but 200+ transitive packages for the same API) |
| Frontend | Vanilla ES2022 + 5 classic scripts, one CSS file | No build chain, no supply chain, instant boot, CSP-friendly | React/Vite (faster to write, adds toolchain + 300 MB node_modules) |
| PWA | Manifest + service worker + install prompt + SSE | One codebase; installable; offline shell | Native apps (2× cost, store review, iOS limits anyway) |
| Storage (now) | JSON document store, atomic writes | Inspectable, no infra | — |
| Storage (target) | Postgres 17 + RLS + partitioning | Tenant isolation at the DB layer, PITR, extensions | MongoDB (weaker relational guarantees for money/inventory) |
| Crypto (now) | ChaCha20 + HMAC-SHA256, scrypt | Pure stdlib, correct primitives | AES-GCM (needs a library — swap is one function) |
| Crypto (target) | Envelope AES-256-GCM via KMS/HSM, per-tenant DEKs | Rotation, audit, blast-radius control | Single app-wide key |
| Voice | Provider-abstracted speech-to-speech | Latency + language fit; swap without rewrite | Hard-coded vendor |

## 3. Backend specification

### 3.1 Modular monolith (now) → service split (when load demands)

| Module | File | Split trigger |
|---|---|---|
| API + routing + RBAC | `app/api.py` | > 400 req/s sustained |
| Domain/AI runtime | `app/agents.py` | model fan-out > 50 concurrent turns |
| Persistence | `app/store.py` | any second writer (immediate) |
| Crypto/guardrails | `app/security.py` | HSM integration |
| Verification | `app/redteam.py` | CI integration |

### 3.2 Invariants (must survive every migration)

1. `tenant_id` is derived from the verified session, never from client input.
2. Every mutation writes an audit entry in the same transaction (today: same call; target: same row-locked transaction).
3. No handler blocks longer than 2 s; long work becomes a job with a handle.
4. Idempotency keys on every money/inventory/communication write.
5. Errors return a stable code + trace id; internals never leak.

### 3.3 Eventing and integrations

- **Outbound:** signed webhooks (`X-RE-Signature: t=<ts>,v1=<hmac>`), retries 1m/5m/30m/2h/6h, dead-letter with replay, 24h idempotency.
- **Inbound:** partner lead webhooks validated by signature + source IP allowlist; dedupe on blind index.
- **Universal connectability:** REST action, CSV/SFTP drop, email-in, Zapier/Make/n8n, MCP. Zero-integration completeness is a product guarantee (`docs/04-API-AND-WEBHOOKS.md`).

### 3.4 Data layer targets

- Postgres 17, UUIDv7 keys, `tenant_id` + RLS on every tenant table, partition `messages`/`call_turns`/`webhook_deliveries`/`audit_log` by month.
- Vector search: one index namespace per tenant, enforced by query-time filter *and* separate index; embeddings treated as personal data.
- Object storage: SSE-KMS, per-tenant prefixes, short-lived presigned URLs (≤5 min), virus scan before first read.

## 4. Cryptography

> Key storage, derivation, rotation and the leak runbook are specified separately in
> **[11-SECRETS-MANAGEMENT.md](11-SECRETS-MANAGEMENT.md)**. This section covers the primitives and the
> parameters; that one covers where the root lives and what happens when it is lost or stolen., key management & data protection

### 4.1 As built (`app/security.py`)

| Property | Implementation |
|---|---|
| Field encryption | ChaCha20 (RFC 8439) keystream + HMAC-SHA256 tag, encrypt-then-MAC |
| AAD binding | `tenant_id` is authenticated as associated data → ciphertext cannot be transplanted across tenants |
| Blind index | `HMAC-SHA256(index_key, normalise(phone))` — deterministic dedupe, not reversible |
| Passwords | scrypt N=2¹⁵, r=8, p=1, 16-byte salt, constant-time compare, 6-failure lockout |
| Session tokens | base64url payload + HMAC-SHA256, 8h TTL, `jti` revocation list, role change invalidates |
| CSRF | HMAC of session token, double-submit |
| Audit | SHA-256 hash chain with `prev_hash`; verification endpoint returns broken index |

### 4.2 Target architecture (phase 2)

```
KMS/HSM (FIPS 140-3 L3)
   └── Tenant Master Key (TMK, non-exportable)
         └── Tenant DEK (AES-256-GCM, rotated 90d, versioned)
               └── Field ciphertext   (AAD = tenant_id ‖ table ‖ column ‖ row_id)
Search: blind index (HMAC-SHA256) + optional order-revealing index only for non-sensitive ranges
Tokens: opaque, hashed at rest (SHA-256), never logged
```

**Rules**
- Keys are never in the application config, never in the repo, never in an image layer.
- Decryption happens only in the service that needs the plaintext; the API returns masked values by default.
- Key compromise playbook: revoke → re-encrypt with new DEK version → rotate blind-index key with dual-write migration → invalidate all sessions.
- Deletion: crypto-shred by destroying the DEK version, which makes the ciphertext unrecoverable (documented as DPDP erasure evidence).

### 4.3 Post-quantum readiness **[FORECAST, high confidence]**

NIST's ML-KEM (FIPS 203) and ML-DSA (FIPS 204) are shipping in mainstream libraries; **harvest-now-decrypt-later** makes long-lived buyer PII (passport scans, title documents, loan files kept 7+ years) the real exposure, not session traffic.

| Year | Action |
|---|---|
| 2027 | Hybrid TLS (X25519MLKEM768) at the edge; nothing else changes |
| 2028 | ML-DSA signatures for webhook signing and licence artefacts (dual-sign with Ed25519) |
| 2029 | ML-KEM-wrapped DEKs; re-encrypt cold archives |
| 2030–31 | Crypto-agility audit: every algorithm identified by OID/version in ciphertext headers (we already prefix-version ciphertext format) |

**Do not** invent crypto. **Do** version ciphertext: our `seal()` output is a self-describing blob; the production format adds `v2:` with algorithm id.

## 5. AI & agent security

### 5.1 The 2026 threat picture

OWASP's **LLM Top 10 (2026)** reordered around agency: prompt injection still #1, **excessive agency up to #3**, unbounded consumption up to #6, hidden context exposure broadened from system-prompt leakage `[R7][R8]`. OWASP's **Agentic Top 10** extends this to tool-level attacks now seen in the wild: tool poisoning (malicious instructions in tool metadata), schema poisoning, tool shadowing, command injection through agent input, shadow MCP servers, and context over-sharing `[R9]`.

MCP went from a 2024 Anthropic spec to infrastructure: ~97M monthly SDK downloads and ~41% of surveyed organisations running it in production by 2026, with **security as the top blocker**; independent scans found 30–82% of public MCP servers with exploitable flaws and only a minority using authentication `[R1][R2][R3]`. 30+ CVEs hit MCP servers/clients in early 2026, including an RCE (CVSS 9.6) affecting 437k+ environments `[R1]`. The 2026-07-28 spec made the core stateless and moved OAuth 2.1 from optional toward default `[R4][R3]`.

**Design consequence:** the tool-calling layer is where enterprise AI risk actually lives. Guard the tools, not just the prompt.

### 5.2 Control architecture (as built)

```
user input / document / tool result        ← all untrusted
        │
        ├─▶ [1] Inspector (16 patterns + PII): score 0–100 → allow / redact / quarantine / block
        │        app/security.py:inspect_text
        ├─▶ [2] Policy: tenant kill switch · agent status · spend cap
        ├─▶ [3] Tool manifest: allowlist ⊆ declared scopes, recomputed per call
        ├─▶ [4] Plan: irreversible + outbound → approval queue, never silent
        ├─▶ [5] Model call (residency-routed, no secrets in context)
        ├─▶ [6] Output inspection + secret/PII redaction
        └─▶ [7] Audit: action, guardrail decision, cost, latency
```

Fail-closed rule: `block` **or** `quarantine` ⇒ zero model output, zero tool calls, human escalation (`app/agents.py`). This is verified by `RT-007`, `RL-501`, `RL-505`.

### 5.3 Indirect injection is the hard case

Direct injection is a filter problem; **indirect** injection (a hostile PDF, a portal listing, a web page, a tool result) is an architecture problem. Controls, in order of value:

1. **Privilege separation (dual-LLM pattern):** a privileged planner that never reads untrusted content, plus a quarantined reader that returns schema-validated summaries only `[R2]`. Target: phase 2 for document intake.
2. **Structural delimiters + provenance tags:** untrusted content is wrapped and labelled; the model is instructed that tagged content is data, not instructions. Cheap, reduces but does not eliminate.
3. **Least agency:** the agent literally cannot do the damaging thing — the tool isn't in its manifest.
4. **Human approval on irreversible operations**, showing the *raw operation*, never the model's summary of it.
5. **Canary tokens** in system context to detect exfiltration attempts; alert on any echo.
6. **Cross-server containment:** one tool session per task, no shared session across servers, per-resource OAuth tokens (RFC 8707) so a token minted for server A cannot be replayed at server B `[R2]`.

### 5.4 MCP gateway specification (as designed, partially built)

| Control | Requirement |
|---|---|
| Inventory | Every server registered, owner-assigned, versioned; "shadow MCP" scanning in CI |
| Auth | OAuth 2.1 + PKCE, resource indicators, ≤1h access tokens with refresh |
| Scope | Per-tool scope declaration; widening requires human re-consent |
| Description integrity | Tool descriptions hashed and stored at approval time; change ⇒ re-approval (`list_changed` is not enough) |
| Egress | Tool results size-capped, schema-validated, treated as untrusted |
| Logging | Full tool call log with arguments hash, decision, latency, cost |
| Kill | Per-tool disable is instant and tenant-scoped |

### 5.5 Jailbreak defence in depth

| Layer | Mechanism | Residual risk |
|---|---|---|
| Input | Pattern + heuristic inspector (ours), plus a classifier model in phase 2 | Novel phrasings, cross-modal payloads |
| Instruction | Role hierarchy in prompt; untrusted content in tagged blocks | Model may still follow data |
| Tool | Allowlist + scope revalidation + approvals | Legit tool used for illegitimate intent |
| Output | Secret/PII redaction, claim-set validation, no `eval`/HTML sinks | Semantic misinformation |
| Behaviour | Spend caps, rate limits, anomaly alerts on unusual tool sequences | Slow misuse |
| Human | Approval queue with raw operations; sampled review of AI calls | Reviewer fatigue |

**Position:** prompt-level defence never reaches 100%. Budget for the model being wrong; design so being wrong is survivable. That is why every dangerous action is gated outside the model.

### 5.6 Model supply chain & residency

- Provider allowlist with signed model identifiers; no dynamic model strings from tenant input.
- Router: high-sensitivity → on-prem; medium → India-resident; frontier only with owner consent (`app/agents.py:route_model`).
- AIBOM per release: model ids/versions, adapter hashes, dataset sources, eval results.
- Shadow evaluation before promotion: any learned skill runs against a held-out transcript set; promotion requires the human gate.

### 5.7 Agent evaluation harness (phase 2)

| Metric | Target |
|---|---|
| Injection resistance (curated corpus, 500+ cases) | ≥ 99% blocked/quarantined |
| Task success on gold conversations | ≥ 85% |
| Hallucinated price/legal claim rate | 0 (hard-fail, claim-set enforced) |
| Tool-call precision (no unnecessary writes) | ≥ 95% |
| Escalation recall (should have called a human) | ≥ 90% |

| CSRF | Double-submit + Origin check | `RL-401/402` |

mTLS with short-lived certificates, SPIFFE-style workload identity, no long-lived shared secrets,
network policies default-deny, and admin/control-plane endpoints on a separate listener with IP allowlist.

## 7. Injection, malware and host hardening

### 7.1 Injection matrix (class → control → test)

| Class | Control | Test |
|---|---|---|
| SQLi | Parameterised queries only (target: Postgres); no string-built SQL | `RL-301` |
| XSS | Output escaping at every sink (`esc`), CSP without inline script, JSON content type | `RL-302/303` |
| SSTI | No template engine over user data; pages are f-string + escape | `RL-310` |
| Command injection | No shell execution in the app tier; agent tools are RPC-style, allowlisted | `RT-007` corpus |
| Path traversal | `normpath` + prefix check + no symlinks in web root | `RL-304`, pytest |
| CSV formula injection | Prefix `'` for `= + - @ TAB CR` on export | `RT-008`, `RL-308` |
| Deserialisation | JSON only, `Content-Type` enforced, 1 MB body cap, no pickle/yaml-unsafe | `RL-307` |
| Header/CRLF | Framework-level header validation; no user data in headers | `RL-306` |
| Unicode/normalisation | NFC normalisation, zero-width stripping, blind-index dedupe | `RL-309` |
| Log injection | Structured logs, control chars stripped, PII scrubbed before write | code review |
| Prototype pollution | No object merge from request bodies; allowlist pick | `RT-009` |

### 7.2 Malware, ransomware and data-theft hardening

| Layer | Control |
|---|---|
| Uploads | Type allowlist, magic-byte check, size caps, AV/CDR scan before first read, stored outside web root, served via short-lived signed URL with `Content-Disposition: attachment` |
| Ransomware | Immutable backups (object lock, 30-day retention), tested restore, offline copy, least-privilege service accounts, no SMB |
| Exfiltration | Egress allowlist, DLP on bulk export, anomaly alerts on mass read, per-tenant export quotas, no `data.bulk_export` without approval |
| Host | Minimal container, non-root, read-only FS, seccomp, no shell, CIS benchmark, patching ≤ 24 h for CVSS ≥ 9 |
| Secrets | Vault/KMS, no env-file secrets in prod, automatic rotation, secret scanning in CI |
| Endpoint | EDR on operator laptops (BYOD policy), disk encryption, managed updates |

### 7.3 Case study: the October 2026 PHP2Shell wave and AI-assisted post-exploitation

**What happened.** On 21 Oct 2026 the PHP project shipped emergency releases for two memory-safety
flaws in the runtime — **CVE-2026-109618 / CVE-2026-109619** (CVSS v4.0 9.2) — allowing
unauthenticated remote code execution in default configurations; an application with clean code was
still exposed if it ran an affected interpreter version. Fixed releases: 8.5.12, 8.4.27, 8.3.36,
8.2.35. A third issue (**CVE-2026-115560**) later required `session.upload_progress.enabled=0` as a
workaround. The vulnerabilities had existed for years and were found with frontier AI models; one
researcher described an LLM turning the pattern into a reusable *skill* that surfaced variants `[R5][R6]`.

**What made the follow-on intrusion fast.** Reporting describes an attacker reaching password hashes
and MFA secrets and attempting Domain Admin escalation **within two hours**, with a European
government entity as the case study. Crucially, commands were wrapped in machine-parseable
section-header delimiters (`==SHELLUSER==`, `==PASSWD==`) — the signature of an **agentic attacker**
automating post-exploitation, not a human typing `net user /domain`. C2 over I2P was reported.
Amazon logged exploitation attempts four days before the patch, and Cloudflare reported millions of
attempts after disclosure `[R5][R6]`.

**Lessons we encode**

1. **Runtime-level exposure beats code-level virtue.** Inventory interpreters, not just dependencies. Our stack ships no PHP; the control is an *interpreter patch SLA* (CVSS ≥ 9 ⇒ 24 h) and version pinning with automated update PRs.
2. **Exploit discovery is now AI-accelerated.** Mean time from "pattern spotted" to "weaponised variant at scale" is collapsing. Assume public exploit within 48 h of disclosure.
3. **Agentic attackers move in hours.** Detection must be tuned for machine-speed recon: sequential enumeration, hash-dump command batches, credential-store reads, NTLM relay, and outbound tunnels (I2P/Tor) from servers.
4. **Fail-closed agentic stacks.** If an agent's guardrail or tool gateway degrades, it stops — never "continues in best-effort mode". We implement exactly that (`block`/`quarantine` ⇒ no execution).
5. **Your own coding agents are an attack surface.** A planted `AGENTS.md`/`CLAUDE.md` in a working directory can steer an AI coding agent into running malware or leaking a token; the trust boundary is the *launch directory* `[R6]`. Policy: coding agents run only inside the repo, never from home/Downloads; instruction files are code-reviewed and signed off.
6. **Memory-safe by default.** For new high-risk edge components (parsers, media handling) choose Rust/Go over C extensions; one fewer decade-old memory bug is one fewer PHP2Shell.

### 7.4 Detection rules shipped in phase 2

| Rule | Signal | Action |
|---|---|---|
| Bulk-read anomaly | One session reads > 5× its 30-day p95 of contact records | Throttle + alert |
| Mass message attempt | > 200 outbound in 5 min per tenant | Halt + owner notification |
| Agent loop | Same tool called > 8× in 60 s | Circuit breaker |
| Exfil shape | Response contains > 100 PII spans to a non-approved client | Block + alert |
| Command-shaped output | Log line matches `==SHELLUSER==`-style delimiters or `net user /domain` patterns | Page on-call |
| Credential store access | Process touching `/etc/shadow`, SAM, LSASS (host agent) | Isolate host |
| Egress to anonymity network | I2P/Tor connection from a server | Block egress + incident |

## 9. Observability, incident response, resilience

### 9.1 Telemetry

- **Logs:** structured JSON, PII-scrubbed at source, request id/trace id, tenant id (never PII), 90-day hot / 1-year cold.
- **Metrics:** RED (rate/errors/duration) per route, gold signals for voice (turn latency p50/p95), per-tenant cost meters, guardrail decisions by category, approval-queue age.
- **Traces:** OpenTelemetry spans across API → agent → model → tool.
- **Alerts:** burn-rate SLOs; security alerts route to on-call with a runbook link.

### 9.2 Incident response (DPDP + CERT-In timelines)

| Phase | Target | Artefacts |
|---|---|---|
| Detect | < 15 min for critical alerts | SIEM rule id, alert payload |
| Triage & contain | < 1 h | Kill switch, token revocation, tenant isolation |
| CERT-In report | ≤ 6 h | Incident form, affected systems, indicators |
| DPDP Data Protection Board + principals | "without delay", runbook target ≤ 72 h `[R16]` | Breach description, categories, mitigation, contact |
| Post-incident | ≤ 5 days | Blameless review, control changes, regression test added to REDLINE |
| Evidence | 7 years | Hash-chained audit export, WORM copy |

### 9.3 Resilience

- Backups: hourly WAL + daily full, object-lock 30 days, restore drilled monthly.
- Degradation ladder: model provider down → deterministic templates; voice provider down → callback queue; DB read-only → operator banner, no silent failure.
- Kill switch tested quarterly and proven in `RL-701`.

### 9.4 Threat model (STRIDE + agentic)

| Threat | Vector | Control |
|---|---|---|
| Spoofing | Session/API token theft | HttpOnly+SameSite, HMAC tokens, 8h TTL, jti revocation, MFA/passkeys |
| Tampering | Forged tenant id, mass assignment | Session-derived tenancy, field allowlists, audit chain |
| Repudiation | "The AI did it" | Per-action audit with actor + guardrail decision + model id |
| Information disclosure | Cross-tenant read, PII in logs/prompts | RLS/blind index, masking by role, redaction, egress allowlist |
| Denial of service | Expensive prompts, mass export | Rate limits, spend caps, quotas, circuit breakers |
| Elevation | Role claim tampering, BFLA | Signed tokens, per-route role rank, re-auth on role change |
| **Tool poisoning / shadowing** | Malicious MCP server metadata | Signed descriptions, hash-on-approval, one session per task `[R2]` |
| **Indirect injection** | Hostile document/web page | Dual-LLM, provenance tags, least agency, approvals |
| **Agentic post-exploitation** | Fast recon after RCE (`PHP2Shell` class) | Interpreter patch SLA, machine-speed detection, egress monitoring `[R5]` |
| **Supply chain** | Malicious package/model/adapter | Zero-dependency tier, SBOM/AIBOM, signed artefacts, provenance |

**Standing decision:** we adopt standards we can *switch off*. Every external protocol sits behind an
adapter; every model behind a router; every vendor behind a kill switch. The five-year risk is not
missing a wave — it is being unable to leave one.
